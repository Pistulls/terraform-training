What Infrastructure as Code is

Infrastructure as Code (IaC) means defining servers, networks and services in configuration files, then letting a tool create and change them, instead of clicking through consoles or running one-off scripts.

resource "aws_instance" "web" {
  ami           = "ami-0abc1234"
  instance_type = "t3.micro"
}
# You describe the end state. Terraform works out the API calls.

Declarative, not imperative

  • Imperative tools take a list of steps: "create an instance, then attach a volume". Running the steps twice usually makes two of everything.
  • Declarative tools, including Terraform, take the desired end state. The tool compares it with what exists and only makes the changes needed to close the gap.
  • Because of that, applying the same configuration twice in a row changes nothing the second time. That property is called idempotence.

Terraform configuration is written in HCL (HashiCorp Configuration Language) in .tf files. A JSON variant, .tf.json, exists for machine-generated configuration.

Terraform is a provisioning tool: it creates and manages the infrastructure itself. Configuration management tools such as Ansible, Chef or Puppet mostly install and configure software on servers that already exist. They are often used together.

On the exam"Describe the desired state and let the tool work out the steps" is declarative. Terraform is declarative, even though the order of operations is worked out for you behind the scenes.

Why teams use IaC

Once infrastructure is code, it gets the same tools software already has: version control, review, reuse and automation.

Multi-cloud, hybrid and service-agnostic

Terraform uses one language and one workflow for any platform that has a provider. That's what makes it useful across several clouds, on-premises and SaaS.

terraform {
  required_providers {
    aws        = { source = "hashicorp/aws" }
    azurerm    = { source = "hashicorp/azurerm" }
    cloudflare = { source = "cloudflare/cloudflare" }
  }
}
# One configuration, one plan, one apply, three platforms.
  • Multi-cloud: manage AWS, Azure and Google Cloud resources with the same tool, and even in the same configuration, with dependencies across them.
  • Hybrid cloud: on-premises platforms such as VMware vSphere have providers too, so private and public infrastructure share a workflow.
  • Service-agnostic: providers aren't limited to clouds. GitHub repositories, Kubernetes objects, DNS records, Datadog monitors and PagerDuty schedules can all be managed the same way.
  • Because the workflow is the same everywhere, teams learn init, plan and apply once, and the same review and automation process covers everything.
On the examTerraform is cloud-agnostic, but the configuration isn't portable. An aws_instance block can't deploy to Azure; you'd write azurerm_linux_virtual_machine instead. What's shared is the language, workflow and tooling, not the resource definitions.

How Terraform uses providers

Terraform core knows nothing about any cloud. Providers are separate plugins that teach it the resource types and data sources for one platform, and make the API calls.

  • Terraform core reads configuration, builds the dependency graph, manages state and works out the plan.
  • Providers are separate executables. Core talks to them over RPC. Each one defines resource types such as aws_instance, and translates create, read, update and delete into API calls.
  • Every resource type starts with its provider's local name: aws_instance comes from aws, random_id from random.
  • Providers are versioned and released separately from Terraform itself, so you can upgrade one without the other.

Where providers come from

Each provider has a source address: [HOSTNAME/]NAMESPACE/TYPE. The hostname defaults to the public Terraform Registry, registry.terraform.io, so hashicorp/aws means registry.terraform.io/hashicorp/aws.

required_providers and version constraints

Declare every provider in the terraform block with a source and a version constraint. Pin Terraform's own version with required_version.

terraform {
  required_version = ">= 1.12.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"        # any 6.x at 6.0 or above, never 7.0
    }
    random = {
      source  = "hashicorp/random"
      version = ">= 3.6, < 4.0"
    }
  }
}
OperatorMeaning
= 1.2.0 or 1.2.0Exactly this version
!= 1.2.0Any version except this one
>, >=, <, <=Comparisons. Combine with commas: ">= 1.2, < 2.0"
~> 1.2.0Pessimistic: only the rightmost number may increase, so 1.2.x
~> 1.21.2 and above within 1.x, so up to but not including 2.0
  • The key (aws) is the provider's local name, used in provider blocks and resource type prefixes.
  • required_version constrains the Terraform CLI, not providers. If the running version doesn't match, every command stops with an error.
  • The terraform block can only contain constant values. Variables and functions aren't allowed in it.
  • Reusable modules should set a minimum version (>=). Root modules can set tighter limits, such as ~>.
On the examExpect to work out what ~> allows. Count the numbers: ~> 4.1.0 allows 4.1.1 but not 4.2.0. ~> 4.1 allows 4.9.0 but not 5.0.

The dependency lock file

.terraform.lock.hcl records the exact provider versions and checksums that init chose, so every run and every teammate uses the same ones. Commit it to version control.

provider "registry.terraform.io/hashicorp/aws" {
  version     = "6.14.1"
  constraints = "~> 6.0"
  hashes = [
    "h1:Abc...=",
    "zh:0123...",
  ]
}
  • On the first init, Terraform picks the newest version that matches your constraints and writes it to the lock file.
  • On later runs, it installs the locked version, even if a newer one matching the constraint exists.
  • To move to a newer version within your constraints, run terraform init -upgrade. It updates the lock file.
  • If you change a constraint so the locked version no longer matches, init fails until you run it with -upgrade.
  • The hashes let Terraform verify downloads. If teammates use other operating systems, add their hashes with terraform providers lock -platform=linux_amd64 -platform=darwin_arm64.
Commit to GitDon't commit
.tf files, .terraform.lock.hcl.terraform/ (downloaded plugins and modules), terraform.tfstate*, saved plan files, .tfvars containing secrets
On the examThe lock file tracks providers only. Module versions are not locked; Terraform picks the newest matching module version each time it installs modules. A configuration with only a constraint and no lock file can quietly pick up a new provider version.

Configuring providers, and using several

A provider block sets options such as region or project. A single configuration can use as many different providers as it needs.

provider "aws" {
  region = var.region
}

provider "random" {}          # optional: no settings needed

resource "random_pet" "suffix" {}

resource "aws_s3_bucket" "logs" {
  bucket = "logs-${random_pet.suffix.id}"   # one provider feeding another
}
  • provider blocks are optional when a provider needs no settings. Terraform creates an empty default configuration for it.
  • Each resource uses the provider whose local name matches its type prefix. You don't need to connect resources to providers yourself.
  • Resources from different providers can reference each other, and Terraform orders them from those references like any other dependency.
  • Provider blocks can use input variables, but not values only known after apply.
  • Don't put credentials in provider blocks. Use environment variables such as AWS_ACCESS_KEY_ID, a shared credentials profile, or the dynamic credentials covered in the HCP Terraform unit.

To use the same provider with two configurations, such as two AWS regions, you add a second block with alias. That gets its own lesson in the Modules and providers unit.

On the examProvider configuration belongs in the root module. Child modules should declare which providers they need with required_providers, and inherit the configuration.

How Terraform uses state

Every plan compares three things: your configuration, the state file, and the real infrastructure. State is the link between the first and the last.

  1. Refresh: Terraform reads the current settings of every object recorded in state from the provider's API.
  2. Compare: it compares the refreshed values with what the configuration asks for.
  3. Plan: resources in the configuration but not in state are created. Resources in state but no longer in the configuration are destroyed. Differences are updated or replaced.
  4. Apply: after the changes, Terraform writes the new values back to state.
  • By default state is a JSON file, terraform.tfstate, in the working directory. The previous version is kept as terraform.tfstate.backup.
  • Terraform only manages objects recorded in its state. An object created by hand in the console is invisible to it until you import it.
  • State holds every attribute, including passwords and keys, in plain text. Treat the file as a secret and don't commit it.
  • Inspect state with terraform show and terraform state list. Don't edit the file by hand.

Backends, locking, drift and refactoring come later in the State management unit.

On the exam"Remove a resource block and apply" destroys that resource, because it's still in state but no longer in the configuration. Deleting the state file doesn't destroy anything; Terraform just forgets the objects exist.

Run it after cloning a configuration, and again whenever you add or change a provider, a module source or version, or the backend.

terraform validate

validate checks that the configuration is syntactically valid and internally consistent. It doesn't contact any cloud API or read remote state.

It catches:

  • HCL syntax errors, such as a missing brace
  • Unknown arguments or blocks for a resource type, and missing required arguments
  • References to variables, resources or modules that don't exist
  • Type mismatches that can be detected without real values

It doesn't catch:

  • Values the cloud would reject, such as an AMI ID that doesn't exist or an invalid instance type
  • Permission or credential problems
  • Name clashes with existing infrastructure
  • It needs init first, because it uses each provider's schema to check arguments.
  • It doesn't need input variable values to be set.
  • -json prints machine-readable results for editors and CI. -no-color strips colour codes for logs.
  • plan and apply validate automatically, so you don't have to run it separately, but it's a quick check in CI and while editing.
On the examContrast the two: fmt fixes layout and needs no init. validate checks correctness and does need init. Neither talks to the cloud provider's API.

terraform apply

apply makes the changes. With no plan file it creates a new plan, shows it and asks you to type yes. With a saved plan file it applies that plan straight away.

terraform apply                         # plan, prompt, apply
terraform apply -auto-approve           # plan and apply without prompting
terraform plan -out=tfplan
terraform apply tfplan                  # no prompt; applies exactly this plan
  • Without a plan file, apply accepts all the planning options: -var, -var-file, -replace, -target, -refresh-only, -destroy.
  • With a plan file, those options aren't allowed, because the plan has already been decided.
  • If state has changed since a saved plan was made, Terraform rejects it as stale. Plan again.
  • Independent resources are changed in parallel, 10 at a time by default (-parallelism=n).

When something fails

  • Terraform doesn't roll back. Changes that succeeded stay, and are recorded in state.
  • If a resource was created but then failed, for example a provisioner errored, it is marked tainted and replaced on the next apply.
  • Fix the cause and run apply again. Terraform picks up where it left off.
On the exam-auto-approve skips the prompt. It's for automation, and it's never needed with a saved plan file, which counts as approved already.

terraform destroy

destroy removes every object the current configuration and state manage. It is an alias for terraform apply -destroy.

terraform plan -destroy          # preview only
terraform destroy                # plan, prompt for "yes", destroy
terraform destroy -auto-approve  # no prompt
terraform destroy -target=aws_instance.web   # one resource and its dependents
  • It accepts the same options as apply, such as -var, -auto-approve and -target.
  • Objects are destroyed in reverse dependency order: dependents first.
  • Only objects in this workspace's state are affected. Anything created outside Terraform is left alone.
  • A resource with lifecycle { prevent_destroy = true } makes the whole destroy fail with an error.
  • To destroy just one resource in normal use, remove its block from the configuration and run apply. That's preferred over -target.
On the exam"Preview what destroy would do" is terraform plan -destroy. "Equivalent command" is terraform apply -destroy. After a destroy, the configuration files and state file still exist; only the infrastructure is gone.

Resources manage, data sources read

A resource block creates and owns an object. A data block only looks up information about something that already exists.

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id   # read from the data source
  instance_type = "t3.micro"
}
  • Data sources come from providers, just like resource types. The arguments are query filters, and the attributes are what the provider returns.
  • Reference them with the data. prefix: data.TYPE.NAME.ATTRIBUTE.
  • Terraform never creates, changes or destroys anything through a data source. Removing a data block deletes nothing.
  • Typical uses: look up an AMI ID, an existing VPC, the current account ID, or outputs from another configuration.
On the exam"Use existing infrastructure that Terraform doesn't manage" or "fetch information defined outside this configuration" means a data source. "Bring an existing object under Terraform management" means import, which comes later.

When a data source is read

Terraform reads data sources during plan if it can, and postpones the read to apply if the query depends on values that aren't known yet.

  • If every argument is known at plan time, the data source is read during the plan and its results appear in the plan.
  • If an argument depends on something (known after apply), such as the ID of a resource that is about to be created, the read is deferred until apply. Anything that uses its results is also unknown in the plan.
  • Adding depends_on to a data source also defers the read whenever the dependency has pending changes. This is one reason to avoid depends_on on data sources unless you need it.
  • Data sources are re-read on every plan, so their results can change between runs, for example most_recent = true picking up a newer AMI.

Data sources accept the meta-arguments count, for_each, provider, depends_on and lifecycle. In lifecycle, only precondition and postcondition apply to them.

On the examA data source's results are stored in state, but Terraform doesn't "manage" that object. Sensitive values read through data sources end up in state too.

Resource addresses

An address pinpoints one resource instance in state. CLI commands such as -target, -replace, state mv and import all take one.

[module.NAME[KEY].]...TYPE.NAME[KEY]

aws_instance.web                     # single resource, or all instances of it
aws_instance.web[0]                  # count instance (number index)
aws_instance.web["blue"]             # for_each instance (string key)
module.app.aws_instance.web          # resource inside a child module
module.app["eu"].aws_instance.web[1] # inside a module that uses for_each
data.aws_ami.ubuntu                  # data sources start with data.
  • count instances are indexed by number, and for_each instances by string key in quotes.
  • An address without an index means all instances of that resource. An address of just module.app means everything in that module.
  • On a Unix shell, quote addresses that contain brackets and quotes: -target='aws_instance.web["blue"]'.

Splat expressions

aws_instance.web[*].id returns a list of the id of every count instance. It is shorthand for [for i in aws_instance.web : i.id].

Splat only works on lists, so it doesn't work on a for_each resource, which is a map. Use values(aws_instance.web)[*].id instead.

Implicit dependencies and depends_on

Referencing another object creates an implicit dependency automatically. Use depends_on only for hidden dependencies that Terraform can't see from your references.

resource "aws_eip" "ip" {
  instance = aws_instance.web.id      # implicit: created after aws_instance.web
}

resource "aws_instance" "app" {
  # The app reads from the bucket at boot, but nothing here references it
  depends_on = [aws_s3_bucket.data]   # explicit
}
  • Terraform builds a dependency graph from references. Independent objects are created in parallel, 10 at a time by default (-parallelism). Dependent ones wait.
  • Destroy runs in reverse order: dependents are removed first.
  • depends_on takes a list of references to whole resources or modules, not strings and not individual attributes. It works on resources, data sources, modules and outputs.
  • Use it as a last resort. It makes plans more conservative: Terraform shows more values as (known after apply) and defers data source reads.
On the exam"Terraform can't infer the ordering because one resource uses another through software or IAM, not through an argument" means depends_on. If there is a reference, an explicit depends_on is unnecessary.

Declaring input variables

Input variables are a module's parameters. Every argument in the block is optional.

variable "instance_count" {
  type        = number
  default     = 2
  description = "How many web servers to run"
  sensitive   = false   # true hides the value in CLI output
  nullable    = true    # false: passing null uses the default instead
}
  • A variable with no default is required. If no value is supplied, Terraform prompts for it interactively, or errors when run with -input=false.
  • type constrains and converts values. If you leave it out, the variable accepts any type.
  • Other arguments, covered later: validation (custom rules) and ephemeral (never stored in state or plan).
  • Variable names can't be reserved words: source, version, providers, count, for_each, lifecycle, depends_on, locals.
  • In the root module, values come from the CLI, files or the environment. In a child module, values come from arguments in the module block.

Conditionals and for expressions

Two expressions do most of the dynamic work: cond ? a : b chooses between values, and for transforms collections.

# conditional
instance_type = var.env == "prod" ? "m6i.large" : "t3.micro"

# list result: square brackets
upper_names = [for n in var.names : upper(n)]

# map result: curly braces and =>
by_id = { for u in var.users : u.id => u.name }

# filter with if
admins = [for u in var.users : u.name if u.is_admin]

# two symbols: key and value of a map (or index and value of a list)
pairs = [for k, v in var.tags : "${k}=${v}"]
  • The outer brackets set the result type: [ ] makes a tuple (list) and { } makes an object (map).
  • A map result can't have duplicate keys. Add ... after the value to group them instead: { for u in var.users : u.team => u.name... }.
  • Both branches of a conditional should be the same type, or types Terraform can convert to one type.

dynamic blocks

count and for_each repeat whole resources. A dynamic block repeats a nested block inside one resource.

resource "aws_security_group" "web" {
  name = "web"

  dynamic "ingress" {
    for_each = var.ingress_rules        # list or map
    content {
      from_port   = ingress.value.port  # iterator is named after the block label
      to_port     = ingress.value.port
      protocol    = "tcp"
      cidr_blocks = ingress.value.cidrs
    }
  }
}
  • The label ("ingress") is the name of the nested block to generate.
  • Inside content, the current item is LABEL.key and LABEL.value. The optional iterator = rule renames it.
  • Dynamic blocks can't generate meta-argument blocks such as lifecycle or provisioner.
  • Use them sparingly. They make configuration harder to read, so prefer writing blocks out when there are only a few.

create_before_destroy

When a resource must be replaced, Terraform destroys the old one first by default. create_before_destroy reverses that, to avoid downtime.

resource "aws_launch_template" "web" {
  name_prefix = "web-"     # unique names allow old and new to coexist

  lifecycle {
    create_before_destroy = true
  }
}
  • It only matters for replacements (-/+). It has no effect on in-place updates.
  • With it set, the plan symbol becomes +/-: create the new object, switch references to it, then destroy the old one.
  • It fails if the provider requires unique values and the new object would clash with the old, such as a fixed name. That's why it's often paired with name_prefix or random suffixes.
  • Terraform also applies the setting to the resource's dependencies, so the replacement order stays valid.
  • lifecycle takes literal values only. You can't use variables in it.

Variable validation

A validation block rejects bad input values early, with your own error message.

variable "env" {
  type = string
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}

variable "ami_id" {
  type = string
  validation {
    condition     = can(regex("^ami-", var.ami_id))
    error_message = "ami_id must start with \"ami-\"."
  }
}
  • condition must be a boolean expression. When it's false, Terraform stops with an error showing error_message.
  • One variable can have several validation blocks.
  • can() turns an error into false, which is useful with regex.
  • Since 1.9, conditions can also refer to other variables and objects, not only the variable being validated.

Preconditions and postconditions

Put these in a resource's lifecycle to enforce assumptions (preconditions) and guarantees (postconditions). A failure is an error that stops the run.

resource "aws_instance" "web" {
  ami           = data.aws_ami.app.id
  instance_type = var.instance_type

  lifecycle {
    precondition {
      condition     = data.aws_ami.app.architecture == "x86_64"
      error_message = "The AMI must be x86_64."
    }
    postcondition {
      condition     = self.public_dns != ""
      error_message = "The instance must have a public DNS name."
    }
  }
}
  • A precondition is checked before Terraform plans or applies the object. Use it to check inputs and other objects.
  • A postcondition is checked after the object is planned or applied. It can use self to refer to the object's own attributes.
  • They work on resource and data blocks. output blocks support preconditions only.
  • If a postcondition fails during apply, the object has already been changed. The failure stops dependent resources from proceeding.

What sensitive does and doesn't do

sensitive = true hides a value in CLI and plan output. It does not keep it out of state or plan files.

variable "db_password" {
  type      = string
  sensitive = true
}
  • Output shows (sensitive value) instead of the value.
  • Sensitivity carries through expressions. Anything derived from a sensitive value is also sensitive, which is why outputs using one must be marked sensitive.
  • Providers also mark some attributes as sensitive themselves, such as password arguments.
  • sensitive() and nonsensitive() add or remove the marking on a value.
  • Terraform still writes the plaintext value to state, and to any saved plan file.
On the exam"Does marking a variable sensitive encrypt it in state?" No. Protect state itself: use a remote backend with encryption at rest and access controls, never commit state to version control, and treat plan files as secrets too.

Ephemeral values

An ephemeral value is available while Terraform runs but is never written to state or plan files. This is the fix for secrets leaking into state.

variable "db_password" {
  type      = string
  sensitive = true
  ephemeral = true            # 1.10+: never persisted
}

ephemeral "aws_secretsmanager_secret_version" "db" {   # ephemeral resource
  secret_id = aws_secretsmanager_secret.db.id
}
# reference: ephemeral.aws_secretsmanager_secret_version.db.secret_string
  • Three ephemeral constructs arrived in Terraform 1.10:
    • Ephemeral input variables: ephemeral = true
    • Ephemeral outputs: in child modules only, to pass ephemeral values up to a parent
    • Ephemeral resources: ephemeral "TYPE" "NAME" blocks that fetch a value, such as a secret or token, fresh on each run and keep nothing afterwards
  • You can only use an ephemeral value where it won't be persisted: provider configuration, other ephemeral variables and outputs, locals, provisioner and connection blocks, and write-only arguments.
  • Assigning one to an ordinary resource argument is an error, because that argument would end up in state.

Write-only arguments

A write-only argument sends a value to the provider but never stores it. That lets you set real resource properties, like a database password, from ephemeral values.

ephemeral "random_password" "db" {
  length = 20
}

resource "aws_db_instance" "main" {
  # ...
  password_wo         = ephemeral.random_password.db.result  # write-only
  password_wo_version = 1    # bump to push a new password
}
  • Added in Terraform 1.11. Providers offer them on chosen resources, usually with a _wo suffix.
  • They accept ephemeral values, and also ordinary ones.
  • The value is not stored in state or plan, so it shows as null there.
  • Because Terraform keeps no copy, it can't detect when the value changes. Providers therefore pair the argument with a version argument, such as password_wo_version. Changing the version is what triggers an update.
On the examEphemeral values solve "keep secrets out of state". Write-only arguments are how those values reach a managed resource.

Secrets from Vault

Don't hard-code credentials. Fetch them at run time from a secrets manager such as Vault, ideally as short-lived, dynamic secrets.

provider "vault" {}   # address and token come from VAULT_ADDR and VAULT_TOKEN

data "vault_aws_access_credentials" "creds" {
  backend = "aws"
  role    = "deploy"
}

provider "aws" {
  access_key = data.vault_aws_access_credentials.creds.access_key
  secret_key = data.vault_aws_access_credentials.creds.secret_key
}
  • The Vault provider authenticates to Vault, and its data sources or ephemeral resources read secrets.
  • Dynamic secrets are generated on request with a short TTL, so a leaked credential soon stops working.
  • Secrets read through a normal data block still end up in state. Prefer the provider's ephemeral resources where they exist.
  • Good practice overall:
    • Pass credentials through environment variables, which aren't stored in plan files.
    • Mark values sensitive, or ephemeral where possible.
    • Encrypt and lock down remote state.
    • Never commit .tfvars files that contain secrets.

Every .tf directory is a module. The one you run Terraform in is the root; any it calls with module blocks are children.

module "network" {

  • Resources inside a module are addressed as module.network.aws_vpc.this[0].

Module scope: inputs in, outputs out

Modules are sealed. A child sees only the values passed to it, and a parent sees only what the child outputs.

# root/main.tf
module "web" {
  source        = "./modules/web"
  subnet_id     = module.network.public_subnet_id   # pass one child's output into another
  instance_type = var.instance_type                 # pass a root variable down
}

# modules/web/variables.tf
variable "subnet_id" {}
variable "instance_type" {}

# modules/web/outputs.tf
output "public_ip" { value = aws_instance.this.public_ip }
  • A child can't read the root's var.x, locals or resources unless they're passed in as arguments.
  • A parent can't read a child's resources directly, only module.web.public_ip.
  • Each module has its own namespace for variables, locals and resource names, so two modules can both have aws_instance.this.
  • Required child variables (those with no default) must be set in the module block.

provider "aws" {

}

  alias  = "us"
  region = "us-east-1"

  provider = aws.us             # LOCAL_NAME.ALIAS, no quotes
  # ...
}

  • Using several different providers together (aws, azurerm, random) needs nothing special. Each has its own default configuration.
  • provider blocks can use variables, unlike the terraform block, but not values only known after apply.
  • Keep credentials out of provider blocks. Use environment variables or dynamic credentials.

Providers inside modules

Child modules inherit their parent's default provider configurations. Aliased ones must be passed explicitly with providers.

module "dr" {
  source    = "./modules/site"
  providers = {
    aws = aws.us        # the child's "aws" means the parent's aws.us
  }
}
  • Reusable modules should declare which providers they need in required_providers, with a minimum version, but should not contain provider blocks. Configuration belongs in the root.
  • A module that expects aliased configurations declares them with configuration_aliases in its required_providers.
  • A module that contains its own provider blocks is a "legacy" module. It can't be used with count, for_each or depends_on.

What state is for

State is Terraform's record of which real objects belong to which resources in your configuration. Without it, Terraform can't tell what it manages.

  • Mapping: it links aws_instance.web to i-0abc…. Each object should be managed by only one resource address.
  • Metadata: it records dependencies, so Terraform can destroy objects in the right order even after they've been removed from the configuration.
  • Performance: it caches attribute values. Large setups can use -refresh=false to skip refreshing.
  • Syncing: stored remotely, it gives a team one shared source of truth.

State is JSON, in terraform.tfstate by default. Don't edit it by hand. Use terraform state commands or moved, removed and import blocks. It can contain secrets, so protect it like one.

The local backend

With no backend or cloud block, Terraform uses the local backend, which keeps state as a file on your disk.

terraform {
  backend "local" {
    path = "relative/path/to/terraform.tfstate"   # optional; this is the default
  }
}
  • State is written to terraform.tfstate in the root module directory. The previous version is kept as terraform.tfstate.backup.
  • State for non-default CLI workspaces goes in terraform.tfstate.d/<workspace>/.
  • The local backend locks the state using the operating system's file locking.
  • Fine for learning and solo work. It's poor for teams: there's no sharing, the state lives on one laptop, and it's easy to commit secrets to Git by accident.

Remote backends

A backend block stores state in shared, durable storage, usually with locking and encryption.

terraform {
  backend "s3" {
    bucket       = "acme-tfstate"
    key          = "network/terraform.tfstate"
    region       = "eu-west-2"
    encrypt      = true
    use_lockfile = true      # S3-native locking (1.10+); DynamoDB locking is deprecated
  }
}
  • Built-in backend types include s3, azurerm, gcs, consul, pg, kubernetes, http, cos, oss and remote. To use HCP Terraform, use the cloud block instead.
  • A configuration can have only one backend, and it can't also have a cloud block.
  • Backend blocks can't use variables, locals or data sources; values must be literals.
  • Benefits: the team shares state, it's kept safe from lost laptops, it can be encrypted at rest and access-controlled, and concurrent runs are locked out.

Partial configuration and changing backends

State locking

Terraform locks state automatically for any operation that could write to it, so two runs can't corrupt it at the same time.

  • Locking happens without anything to configure, if the backend supports it. Not every backend does.
  • If another run holds the lock, your command fails straight away (unless you set -lock-timeout=60s) and shows who holds it.
  • -lock=false turns locking off. That's dangerous with shared state.
  • If a crash leaves a lock behind: 
    terraform force-unlock LOCK_ID
    It only removes the lock and doesn't touch infrastructure. Use it only when you're sure nothing else is running.
On the exam"Two engineers ran apply at once and one got an error about acquiring the state lock" means locking worked as intended. The fix for a stuck lock is force-unlock, not deleting state.

Drift and refresh-only mode

Drift is when real infrastructure no longer matches state, usually because someone changed it outside Terraform. Refresh-only mode updates state to match reality without touching infrastructure.

terraform plan  -refresh-only   # show what drifted
terraform apply -refresh-only   # accept the drift into state (asks for approval)
  • A normal plan refreshes too, then proposes changes to put infrastructure back to match the configuration.
  • Refresh-only accepts reality: it writes the changes into state and root outputs, and proposes no resource changes.
  • After accepting drift, either update the configuration to match, or the next normal plan will try to revert it.
  • terraform refresh is deprecated. It's an alias for apply -refresh-only -auto-approve, which skips the review step.
  • If a resource was deleted outside Terraform, a normal plan proposes to recreate it.

Refactoring with moved blocks

Renaming a resource or moving it into a module changes its address. Without help, Terraform would destroy the old object and create a new one. A moved block says it's the same object.

moved {
  from = aws_instance.web
  to   = aws_instance.app
}

moved {
  from = aws_s3_bucket.logs
  to   = module.storage.aws_s3_bucket.logs
}

moved {
  from = aws_instance.web[0]          # count to for_each
  to   = aws_instance.web["primary"]
}
  • The plan shows has moved to, with no destroy and no create.
  • It's declarative and reviewed in a plan, which makes it safer than terraform state mv. It also works for everyone else who uses your configuration or module.
  • Keep moved blocks in shared modules so every caller's state migrates. In a root module you can remove them once everyone has applied.
  • Available since Terraform 1.1.

Workspace variables and variable sets

Workspaces hold two kinds of variable. Variable sets let you reuse groups of variables across many workspaces.

  • Terraform variables set input variables, like a .tfvars file. Tick the HCL box for lists, maps and objects.
  • Environment variables are set in the run's shell. Use them for provider credentials (AWS_ACCESS_KEY_ID) and TF_VAR_* values.
  • Marking a variable sensitive makes it write-only: nobody can read it back in the UI or API. It's still available to runs.
  • A variable set is a reusable group of variables. It can apply to the whole organization (global), to projects, or to specific workspaces.

Which value wins

  • A variable set directly on the workspace overrides a set applied through a project, which overrides a global set.
  • A variable defined on the workspace itself overrides any variable set.
  • A priority variable set overrides everything, including workspace variables and values from the CLI. Use it to enforce settings.

Health assessments: drift detection and continuous validation

HCP Terraform can check workspaces on a schedule, between deployments, and alert you when something is wrong. It never changes infrastructure on its own.

Dynamic provider credentials

Rather than storing long-lived cloud keys, HCP Terraform can obtain short-lived credentials for each run, using OIDC workload identity.

  • You set up a trust relationship once: the cloud provider trusts HCP Terraform's identity tokens for a given organization, project or workspace.
  • On each run, HCP Terraform presents a signed identity token and the cloud returns temporary credentials. They expire soon after the run, and there are no static secrets to leak or rotate.
  • You configure it with workspace environment variables, for example TFC_AWS_PROVIDER_AUTH = true and TFC_AWS_RUN_ROLE_ARN.
  • Supported for AWS, Azure, Google Cloud, Vault, Kubernetes and HCP.

AWS: credentials and provider settings

The AWS provider authenticates the same way as the AWS CLI, and checks sources in a fixed order. It stops at the first one that works.

#Credential source, checked in this order
1Arguments in the provider block (access_key, secret_key), which isn't recommended
2Environment variables: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN
3Shared credentials file: ~/.aws/credentials
4Shared config file: ~/.aws/config
5Container credentials (ECS task role, CodeBuild)
6Instance profile, from EC2 instance metadata
provider "aws" {
  region                   = "us-west-2"          # required
  profile                  = "staging"            # or AWS_PROFILE; default is "default"
  shared_credentials_files = ["/opt/aws/credentials"]   # a list
  allowed_account_ids      = ["111122223333"]     # guard rail

  assume_role {
    role_arn     = "arn:aws:iam::444455556666:role/Terraform"
    session_name = "terraform"
  }
}
  • A region is required. It comes from the region argument, AWS_REGION or AWS_DEFAULT_REGION, the profile, or instance metadata.
  • assume_role switches to an IAM role, usually in another account. It can't be set through environment variables, and the AWS root user can't assume roles.
  • Because environment variables come before the shared files, exported keys silently override a profile. The assume-role tutorial has you unset them first.
  • assume_role_with_web_identity is the OIDC version, used for EKS service accounts and CI systems.
  • allowed_account_ids and forbidden_account_ids protect against applying to the wrong account. You can't use both.
  • Since provider v6, most regional resources accept their own region argument, overriding the provider's.
  • Check what the CLI is using with aws configure list. On Windows the shared files live in %USERPROFILE%\.aws\.
On the exam"Credentials work in the CLI, but Terraform uses a different account" usually means exported AWS_* environment variables are overriding the profile. "Run on EC2 with no keys at all" means an instance profile.

AWS: default_tags and the S3 backend

default_tags tags every resource from the provider block. The S3 backend now locks with an object in the bucket instead of DynamoDB.

provider "aws" {
  region = "us-east-2"
  default_tags {
    tags = { Environment = "Test", Service = "Example" }
  }
}
  • A tag with the same key on a resource overrides the default. You can't remove a default key from just one resource.
  • tags shows only the resource's own tags. tags_all shows resource tags merged with default tags. Changing defaults is an in-place update.
  • Exception: aws_autoscaling_group doesn't get default tags, and neither do the instances it launches. The workaround reads data "aws_default_tags" and generates tag blocks with a dynamic block and propagate_at_launch = true.
  • ignore_tags in the provider block makes Terraform ignore tags that other systems add.

S3 backend

terraform {
  backend "s3" {
    bucket       = "acme-tfstate"        # required
    key          = "app/terraform.tfstate" # required
    region       = "us-east-1"           # required (or AWS_REGION)
    encrypt      = true
    kms_key_id   = "arn:aws:kms:..."     # optional customer-managed key
    use_lockfile = true                  # S3-native locking: writes <key>.tflock
  }
}
  • use_lockfile arrived in Terraform 1.10 and defaults to false. DynamoDB locking (dynamodb_table, partition key LockID) is deprecated. You can enable both while migrating.
  • Permissions: s3:ListBucket on the bucket, s3:GetObject and s3:PutObject on the state key, and s3:DeleteObject as well on the .tflock object.
  • Non-default workspaces are stored under env:/<workspace>/<key>, set by workspace_key_prefix.
  • Turn on bucket versioning so you can recover old state.
  • In the backend, assume_role is an attribute written with =, not a block as in the provider.

  vpc_security_group_ids = [module.vpc.default_security_group_id]

Azure: the azurerm provider

azurerm needs an empty features {} block, a subscription ID (from 4.0), and a resource group for almost every resource.

provider "azurerm" {
  features {}                          # required, even when empty
  subscription_id = var.subscription_id  # required from 4.0, or ARM_SUBSCRIPTION_ID
}

resource "azurerm_resource_group" "rg" {
  name     = "myTFResourceGroup"
  location = "westus2"
}

resource "azurerm_virtual_network" "vnet" {
  name                = "myTFVnet"
  address_space       = ["10.0.0.0/16"]
  location            = azurerm_resource_group.rg.location
  resource_group_name = azurerm_resource_group.rg.name   # implicit dependency
}

Azure: the azurerm backend

State is stored as a blob in an Azure Storage container, and Azure Blob Storage's own lease mechanism provides locking.

terraform {
  backend "azurerm" {
    storage_account_name = "acmetfstate"            # required
    container_name       = "tfstate"                # required
    key                  = "prod.terraform.tfstate" # required
    use_azuread_auth     = true                     # recommended: Entra ID, not access keys
  }
}
  • Always required: storage_account_name, container_name and key. resource_group_name is only needed when Terraform looks up the access key for you.
  • Locking and consistency checks use Blob Storage's native capabilities (a blob lease). No extra service is needed.
  • Recommended authentication is Entra ID (use_azuread_auth), ideally with OIDC. The identity needs the Storage Blob Data Contributor role. Access keys (ARM_ACCESS_KEY) and SAS tokens still work but are legacy.
  • Azure Storage encrypts data at rest by default.
  • The Azure get-started "remote state" tutorial actually uses HCP Terraform with a cloud block, not this backend.
On the examDon't confuse use_azuread_auth (backend) with storage_use_azuread (provider block).

Google Cloud: provider, APIs and the gcs backend

The tutorial authenticates with Application Default Credentials (ADC), sets a default project, region and zone, and needs the Compute Engine API enabled before anything works.

gcloud auth application-default login   # stores ADC; the provider finds them automatically
provider "google" {
  project = "my-project-id"   # or GOOGLE_PROJECT
  region  = "us-central1"
  zone    = "us-central1-c"
}

resource "google_compute_instance" "vm" {
  name         = "terraform-instance"
  machine_type = "f1-micro"
  tags         = ["web", "dev"]                         # change: in place
  boot_disk {
    initialize_params { image = "debian-cloud/debian-11" }  # change: forces replacement
  }
  network_interface {
    network = google_compute_network.vpc.name
    access_config {}                                    # empty block = external IP
  }
}
  • Credentials: ADC is the recommended method on a workstation, and an attached service account when running on Google Cloud. A service account key file can be given with the credentials argument or GOOGLE_CREDENTIALS. Google's own GOOGLE_APPLICATION_CREDENTIALS also works, through ADC.
  • Impersonation: impersonate_service_account needs the roles/iam.serviceAccountTokenCreator role on the target account.
  • APIs: each Google Cloud API (Compute Engine, Kubernetes Engine) must be enabled for the project. Otherwise apply fails with a 403.
  • google vs google-beta: preview features live in the separate hashicorp/google-beta provider. A resource only uses it when you set provider = google-beta, even if that's the only provider block you declared.
  • Firewalls block traffic to instances by default. Rules in google_compute_firewall match instances through target_tags.
  • Changing machine_type needs the VM stopped, so set allow_stopping_for_update = true. Changing metadata_startup_script forces replacement.
  • GKE: gcloud container clusters get-credentials writes the kubeconfig entry.

gcs backend

terraform {
  backend "gcs" {
    bucket = "tf-state-prod"     # must already exist
    prefix = "terraform/state"   # workspaces stored as <prefix>/<name>.tfstate
  }
}
  • It supports locking natively, with no separate lock table. Turn on Object Versioning on the bucket.
  • For encryption with your own key, use kms_encryption_key for a Cloud KMS key, or encryption_key for a customer-supplied key. If you lose a customer-supplied key, the state can't be recovered.

Docker and Oracle Cloud

Both get-started tracks use providers outside the hashicorp namespace. Docker talks to a local daemon. OCI authenticates through its own CLI and config file.

Docker

terraform {
  required_providers {
    docker = { source = "kreuzwerker/docker", version = "~> 4.2.0" }
  }
}
provider "docker" {}   # Windows: host = "npipe:////.//pipe//docker_engine"

resource "docker_image" "nginx" {
  name         = "nginx:latest"
  keep_locally = false          # delete the image from the host on destroy
}
resource "docker_container" "nginx" {
  image = docker_image.nginx.image_id
  name  = "tutorial"
  ports {
    internal = 80
    external = 8000             # changing this forces replacement
  }
}
  • host sets the daemon address: the Unix socket unix:///var/run/docker.sock on Linux and macOS, a named pipe on Windows, or ssh:// for a remote host.
  • The provider can't change a running container's port mapping or name, so changing either shows -/+: 1 to add, 1 to destroy.
  • On destroy, the container goes first, then the image.

Oracle Cloud (OCI)

oci session authenticate        # browser login; writes a profile to ~/.oci/config

provider "oci" {
  region              = "us-sanjose-1"
  auth                = "SecurityToken"
  config_file_profile = "learn-terraform"
}
  • auth values: APIKey (the default: tenancy_ocid, user_ocid, fingerprint, private_key_path), SecurityToken, InstancePrincipal (on OCI compute, with no keys), ResourcePrincipal and OKEWorkloadIdentity.
  • Session tokens expire after 1 hour. Refresh them with oci session refresh --profile ....
  • Every resource needs a compartment_id (an OCID). The tutorials use oci_core_vcn and oci_core_subnet.
  • State: the native oci backend (Terraform 1.12 and later) stores state in Object Storage. It needs bucket and namespace, and locks with a lock object. Before 1.12, people used the S3 backend against OCI's S3-compatible endpoint.

Kubernetes and Helm providers

Configure the Kubernetes provider from a kubeconfig or from a cluster's details. Don't create the cluster in the same configuration that uses the provider.

data "aws_eks_cluster" "c" { name = var.cluster_name }

provider "kubernetes" {
  host                   = data.aws_eks_cluster.c.endpoint
  cluster_ca_certificate = base64decode(data.aws_eks_cluster.c.certificate_authority[0].data)
  exec {                                    # short-lived token from the cloud CLI
    api_version = "client.authentication.k8s.io/v1beta1"
    command     = "aws"
    args        = ["eks", "get-token", "--cluster-name", var.cluster_name]
  }
}

# or, locally:  provider "kubernetes" { config_path = "~/.kube/config" }
  • The provider has no default kubeconfig path and doesn't read KUBECONFIG. Set config_path or KUBE_CONFIG_PATH.
  • Same-apply caveat: if the provider's settings come from a cluster created in the same configuration, they are unknown during the plan. That causes intermittent errors. Create the cluster in one configuration and the Kubernetes resources in another, then pass values with data sources, terraform_remote_state or tfe_outputs.
  • kubernetes_manifest can manage any object, including custom resources. It contacts the cluster during plan, so the cluster, and any CRD, must already exist.
  • The helm provider has a nested kubernetes configuration. A helm_release sets repository, chart and values = [file(...)].
  • Typical resources are kubernetes_deployment_v1 and kubernetes_service_v1. Changing replicas is an in-place update.
On the exam"Provision a cluster and deploy apps to it" means two configurations or workspaces, often linked by a run trigger, not one apply.

Checkpoint: platform specifics

Pick an answer to see the explanation.

In what order does the AWS provider look for credentials?

Explicit provider arguments win and EC2 instance metadata comes last. The order matches the AWS CLI. AWS provider

The provider sets default_tags { tags = { Service = "Example" } } and an aws_instance sets tags = { Service = "Custom" }. What tag does the instance get?

Resource-level tags override defaults with the same key. tags_all shows the merged result. Default tags

Which S3 backend setting enables state locking without DynamoDB?

use_lockfile (Terraform 1.10 and later) writes a .tflock object in the bucket. DynamoDB locking is deprecated. s3 backend

You move an aws_instance into a subnet in a different VPC. What does the plan show?

AWS can't move a running instance to a new VPC, so Terraform replaces it. Manage infrastructure (AWS)

Which block must every provider "azurerm" configuration include?

features is required, even if it's empty. From azurerm 4.0, a subscription ID is also required, but that's an argument, not a block. azurerm provider

You set the output of az ad sp create-for-rbac as environment variables. Which one holds the password field?

appId becomes ARM_CLIENT_ID, password becomes ARM_CLIENT_SECRET, and tenant becomes ARM_TENANT_ID. Build infrastructure (Azure)

Which three arguments are always required by the azurerm backend?

resource_group_name is only needed when Terraform looks up the storage access key. azurerm backend

The GCP tutorial's provider block has no credentials argument. Which command makes authentication work?

That command stores Application Default Credentials, which the google provider picks up automatically. gcloud auth login only authenticates gcloud itself. Build infrastructure (GCP)

You change the boot disk image of a google_compute_instance. What does the plan show?

Google Cloud can't replace the boot image of an existing instance. Adding tags, by contrast, is in place. Change infrastructure (GCP)

You declare both google and google-beta providers. How does a resource use a beta-only feature?

Resources default to the google provider, even if only google-beta is configured. google vs google-beta

You change external = 8000 to 8080 in a docker_container's ports block. What happens?

The Docker provider can't change a running container's port mapping, so the change forces replacement. Change infrastructure (Docker)

You export KUBECONFIG=~/.kube/config and leave provider "kubernetes" {} empty. Terraform can't reach the cluster. Why?

The Kubernetes provider has no default config path and ignores KUBECONFIG. kubernetes provider

Terraform runs on an OCI compute instance. Which auth value avoids storing a user OCID, fingerprint and private key?

Instance principal uses the instance's own identity, like an AWS instance profile. APIKey is the default and needs all those values. OCI provider configuration

Mixed mock exam

Fifteen questions across the whole syllabus. Aim for 12 or more.

Which file should you commit to version control?

The lock file pins provider versions for the team. State and plan files can hold secrets, and .terraform/ is a local cache. Lock file

What happens when you run terraform apply tfplan with a saved plan?

Passing the saved plan counts as approval. Planning options aren't allowed with a saved plan. apply

Which command can you run without first running terraform init?

fmt only rewrites text and needs no providers or modules. fmt

You need the AMI ID of the newest image matching a name pattern. What do you use?

Looking up existing objects is the job of a data source. Data sources

Which variable source has the lowest priority, apart from the default?

The order is environment variables, then terraform.tfvars, then the .json version, then *.auto.tfvars, then CLI flags. Precedence

Which meta-argument creates instances that stay stable when an item is removed from the middle of the input collection?

for_each keys instances by name. count keys them by position, so later instances shift. for_each

A health check that fails should warn but never block deployments. Which construct?

Check block failures are warnings. Validate

Which statement about state is true?

State holds plaintext values, including sensitive ones. Protect it with an encrypted remote backend and access controls. Sensitive data

You changed the backend block from one S3 bucket to another and want to keep your state. Which command?

-migrate-state copies the existing state to the new backend. -reconfigure starts fresh without it. init

What's the effect of terraform plan -refresh=false?

Skipping the refresh means Terraform plans against cached state. plan

Which module source address points to a module in your HCP Terraform private registry?

Private registry addresses include the hostname: HOST/ORG/NAME/PROVIDER. Private registry

What does terraform.workspace return?

It's the current workspace name, often used to vary settings per environment. References

Which is not a valid reason to run terraform init again?

Changing resource arguments only needs plan and apply. Init handles providers, modules and backends. init

An S3 bucket was created by hand and you now want Terraform to manage it. What's the recommended approach?

Import brings an existing object under management. A data source only reads it. Import

A team member's run fails with "Error acquiring the state lock". What's the most likely cause?

The lock stops concurrent writes, so wait for the other run or use -lock-timeout. Only force-unlock a lock you know is stale. Locking
